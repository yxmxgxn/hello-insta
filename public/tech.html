ハロー！プロジェクトのメンバーとOGのインスタを、日付と本文から探せるようにした個人サイトです。 どうやって投稿を集め、何を保存し、何をしないと決めているかを説明します。

1. 全体の作り

サイトは Cloudflare Workers と D1（SQLite）で動いています。 投稿は前もって集めてこのサイトのデータベースに入れてあり、検索のたびにインスタへ問い合わせることはありません。 日付の索引と、文章から作った検索用の索引を先に作っておき、1回に新しい方から100件だけを引くので、件数が増えても速さはほとんど変わりません。

どのアカウントを収録するかは、同じ作者のサイト（karin-archive）の「SNS一覧」の元になっている表で決めています。 表を直すと、次の収録から対象も変わります。

2. 投稿の集め方

インスタの公式の仕組み（API）で読めるのは、ビジネスアカウントとクリエイターアカウントだけです。 そこで、アカウントの種類によって集め方を分けています。

ビジネス・クリエイターアカウントの人

  • Instagram（Meta）が公開している公式のAPI（Instagram Graph API の Business Discovery）で集めています
  • 収録プログラムは1時間ごとに動き、各アカウントの最新の投稿を1日1回確かめます
  • 過去の投稿は、APIの利用上限の範囲で少しずつ遡って集めました。上限に達したら、続きは次の回に回します
  • 新しく対象になったアカウントは、過去分がそろうまでにしばらくかかります
  • APIの利用上限の余りで、全員の投稿を週に1回ほど新しい方から読み直しています（周回）。書き直された文章といいねの数を今のものにそろえ、返ってこなくなった投稿を見つけるためです

個人アカウントの人

  • 個人アカウントで収録しているのは、ハロー！プロジェクトの現役メンバーと、OGの一部の人だけです
  • 公式のAPIでは読めないので、最初に作者が、ブラウザに表示された投稿を集めました。画面に出ている投稿のリンクと文章を読み取るだけで、インスタの内部の仕組みに問い合わせることはしていません
  • それ以降の新しい投稿は、RSS のように新着を受け取れる外部のサービスを通して、毎日受け取っています
  • あまり投稿しない人は、作者がときどき見て、手で足しています

どの集め方で入っても、同じ投稿は1件にまとめます。 個人アカウントの人がビジネス・クリエイターアカウントに切り替えたときは、公式のAPIで読んだものに置き換わります。

共同投稿

2人以上の連名の投稿（共同投稿）は、投稿した本人（持ち主）の投稿として扱います。 持ち主がこのサイトで収録していない人のときは、連名に入っているメンバーの投稿として扱います。

3. 検索のしかた

形態素解析（単語への分割）は使わず、投稿の文章を2文字ずつ区切った索引で引いています。 辞書に載らない固有名詞・当て字・口語にも強く、入力した文字列がそのまま並んでいる投稿を探す「部分一致」に近い動きになります。

  • 全角・半角、英字の大文字・小文字は区別しません
  • 記号・句読点・改行・絵文字・ハッシュタグの「#」は無視します
  • 空白で区切ると、すべての語を含む投稿に絞り込みます（100文字まで）
  • 語の前に「-」を付けると、その語を含まない投稿に絞り込みます。含まない語だけでは探せません
  • 2文字以上の語で検索します。1文字だけの語では絞り込みません

結果は新しい投稿から順に並びます。総ヒット件数は表示しません。 数えるだけで、検索そのものより重くなるためです。

4. 表示するもの

一覧には、投稿日時・名前・投稿の種類と、文章の先頭の一部だけを出します。 投稿そのものは、「▶ ここで見る」で開くインスタ公式の埋め込みか、インスタの元の投稿で見てもらいます。 このサイトの役目は、元の投稿を見つけて送り届けることです。

埋め込みは、インスタの「埋め込み」と同じものを置いて、インスタの埋め込み用のプログラム（embed.js）に表示してもらっています。 このプログラムは、最初に「▶ ここで見る」を押したときにだけ読み込みます。 押すと、暗い背景のポップアップで埋め込みを開き、「‹」「›」・「←」「→」キーで一覧の前後の投稿に切り替えられます。前後の投稿は、開いた投稿が出たあとで、裏で1つずつ先に読み込んでおきます（離れたものは捨てます）。

リールのリンクは、インスタの投稿のアドレス（/p/…）にそろえています。 リールのアドレス（/reel/…）だと、別の動画に案内されることがあるためです。

5. わかっている制約

  • 消された投稿は、すぐには消えません。周回で返ってこなかった投稿を、作者が開いて確かめてから消します。年齢制限のかかった投稿など、消えていなくてもAPIが返さない投稿があるため、自動では消しません
  • 文章の書き直しは、周回のときにそろいます。それまでは、前の文章のままのことがあります
  • 個人アカウントの人の投稿は周回できないので、消された投稿や書き直しは、連絡をもらうか作者が気づいたときに直します
  • 写真ごとに文章を付けた複数枚の投稿は、インスタ公式の埋め込みでは、写真ごとの文章が最初から全部まとめて出ます。インスタ側の表示なので、このサイトからは直せません
  • このサイトの投稿数は、インスタのプロフィールの「投稿」の数と少しずれることがあります。共同投稿や、プロフィールの一覧に出さないリールの数え方が違うためです
  • 過去の投稿には漏れがあることがあります。新しい方から遡って集めていて、投稿の多いアカウントでは、とても古い投稿を公式のAPIが返さないことがあるためです。気づいた分は、作者が手で足しています
  • 共同投稿は取れていないことがあります。ほかの人が持ち主で、メンバーが連名に入っている投稿は、集め方によっては拾えません
  • ひらがなとカタカナは別扱い。「りんご」で「リンゴ」は出ません
  • アクセント付きのラテン文字は落ちます（「Café」は「caf」として扱われます）
  • 投稿日時は日本時間で、分までです

6. 取らない・やらないと決めたこと

  • 画像・動画は1バイトも保存しない。文字だけです
  • 文章の全文は画面に出さない
  • コメントの中身・フォロワーなど、投稿以外の情報は取らない。いいねとコメントの数は作者の確認用に持つだけで、画面には出さず、並べ替えにも使わない
  • 鍵をかけている（非公開の）アカウントは取りに行かない
  • 投稿の文章をAIで処理しない。要約・文章の生成・学習には使わない（プログラムを書くのにはAIを使っています）
  • 検索した言葉やアクセスの記録を取らない

消してほしい・載せないでほしいという連絡があれば、そのとおりに対応します。 ご連絡は、karin-archive（同じ作者のサイト）のページ下にある「誤りの報告・追加のご要望」から送ってください。

7. 技術の詳細

ここからは、作りを知りたい人向けの、細かい話です。このサイトが公開している範囲の説明で、鍵や合言葉は含みません。 このリポジトリの docs/instagram.md にも、投稿の取り方のまとめがあります。

構成

  • 画面：HTML・CSS・JavaScript のファイルを、Cloudflare Workers の Static Assets で配信しています。フレームワークは使っていません
  • API：同じ Worker が、/api/posts（投稿の一覧）・/api/calendar（月・日ごとの件数）・/api/accounts（対象のアカウントと件数）・/api/day（その日の投稿）を返します。結果は、Cloudflare のキャッシュに5分置きます
  • データ：Cloudflare D1（SQLite）です。post（投稿）、account（対象のアカウント）、fetch_state（アカウントごとの取得の進み）、post_fts（検索用の索引）の4つが中心です
  • 収録：GitHub Actions のワークフロー（Python）が、毎時起動して、Worker のクローラ用のAPIに結果を送ります。クローラ用のAPIは、合言葉（Bearer 認証）が無いと使えません

公式APIの呼び方

Instagram Graph API の Business Discovery を使います。自分のビジネスアカウントのIDで、相手のユーザー名を渡すと、相手の投稿が返ってきます。 1回の呼び出しは、おおむね次の形です（<…> は入れ替わる部分です）。 

GET https://graph.facebook.com/v23.0/<自分のアカウントのID>
  ?fields=business_discovery.username(<相手のユーザー名>){
    media_count,
    media.limit(50).after(<続きの位置>){
      id,caption,timestamp,permalink,media_type,
      like_count,comments_count,username,media_product_type
    }
  }
  • 1ページは50件です。返事に続きの位置（カーソル）が付いているので、それを after に入れて、古い方へ進みます
  • 取るのは、投稿のID・文章・日時・リンク・種類・いいねとコメントの数・持ち主・リールかどうか、だけです。画像や動画のアドレス（media_url）は聞きません
  • 共同投稿は、持ち主（username）も一緒に聞きます。持ち主が収録している人なら、その人の投稿にします
  • 聞いた項目のどれかが使えない（Meta が返さない）ときは、その項目を外して、頼み直します

利用の上限と、取る順番

  • Meta の利用上限に当たったら（Application request limit reached）、その回は終わりにして、続きは次の回に回します。「頼むデータが多すぎる」（エラーコード1）と断られたら、1回に頼む件数と項目を減らして頼み直し、それでもだめなら、その人の遡りは打ち切ります
  • 1回の収録は、新着 → 遡り → 周回の順で、回数を使います
  • 新着：各アカウントの最新の50件を、1日1回確かめます。全員が同じ時刻に頼むと、上限に当たるので、アカウント名から決まる順番に並べて、1日を等分した「自分の時刻」を、1人ずつ割り当てて、散らしています。優先するアカウントだけは、3時間ごとに確かめます
  • 遡り：新着で使わなかった分の回数で、過去の投稿を、50件ずつ、古い方へたどります。端まで届いたら、完了です
  • 周回：遡りが終わった人の投稿を、別のカーソルで、新しい方から最後まで読み直します。1人7日に1回ほどで、1回の収録で使う回数には上限があります（新着が止まらないようにするためです）

消えたかもしれない投稿の見つけ方

  • 公式APIの返事に入った投稿は、そのたびに post.seen_at（最後に見えた日時）を更新します
  • 周回を読み終えた人で、その周回のあいだに返ってこなかった投稿を、「消えたかもしれない」とします。ただし、周回で返った一番古い投稿より古いものと、周回を始めたあとの投稿は、数えません
  • 年齢制限のかかった投稿など、消えていなくても、APIが返さない投稿があります。そのため、自動では消しません。管理者が、元の投稿を開いて確かめて、「消す」か「残す」を決めます（残したものは、post.keep に印を付けて、次から数えません）

保存と、検索の索引

  • 投稿は、公式APIのものはインスタのメディアID、個人アカウントのものは web:<shortcode> を、IDにします。同じ投稿は1件にまとまり、個人アカウントの人がプロに切り替えたときは、公式APIの分に置き換わります
  • 一覧に出す文章は、先頭の一部だけ（excerpt）です。検索用の索引（post_fts、SQLite の FTS5）には、文章を2文字ずつに区切ったもの（bigram）を入れます。語は、2文字ずつのフレーズにして、MATCH で引きます
  • 空白で区切った語は AND、「-」を付けた語は NOT で組み合わせます（例：ライブ -リハーサル は ("ライ イブ") NOT ("リハ ハー ーサ サル")）
  • 本文が前と同じ投稿は、重い索引を書き直しません（本文の指紋 cap_hash で比べます）
  • 日時は、日本時間の「分」までの文字列で持ちます。日付の絞り込みは、その文字列の大小比較です

表示

  • 投稿を見るときは、インスタ公式の埋め込み（blockquote と、インスタの embed.js）をそのまま使います。「▶ ここで見る」を押したときにだけ読み込みます
  • 前後の投稿は、開いた投稿が出たあとに、裏で1つずつ、先に読み込んでおきます。離れたものは捨てるので、読み込んだままの埋め込みは、いつも最大3つです
  • 埋め込みの規約は、「埋め込み以外の目的で、返ってくる内容を使わない」というものなので、埋め込みのAPI（oEmbed）は、サーバーからは使っていません
